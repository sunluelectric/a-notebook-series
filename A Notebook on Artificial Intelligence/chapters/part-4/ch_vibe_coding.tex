\chapter{Vibe Coding} 

Vibe coding, also known as vibe engineering in some context, is one of the most successful and widely appreciated applications of LLM and agentic AI. Many LLM service providers, such as OpenAI and Anthropic, provide vibe coding services for their subscribers. 

In this chapter, vibe coding is introduced with Anthropic Claude Code used as an example. That said, most things introduced in this chapter can find their counterparts in other vibe coding services such as OpenAI Codex and GitHub Copilot Plan.

Note that vibe coding is continuously evolving. The materials introduced in this notebook reflect developments only up to the time of this writing.

\section{Introduction to Vibe Coding}

Vibe coding is briefly introduced and compared with other coding methods.

\subsection{Coding Spectrum}

In the past few years, \myabb{large language model}{LLM} and agentic AI have revolutionized the way people code. Rather than viewing coding as a set of isolated styles, it is often more helpful to view it as an evolving spectrum of methods and philosophies over time. Up to the time of this writing, this spectrum includes at least the following approaches, and it continues to evolve.

\begin{itemize}
  \item Conventional coding
  \item Coding with autocompletion
  \item Agentic coding
  \item Vibe coding
\end{itemize}

In \mync{conventional coding}, a developer works in a conventional \myabb{Integrated Development Environment}{IDE}, which is essentially a text editor with add-ons. All code is manually typed. The IDE is often able to detect syntax errors and compile the code. Examples include VS Code without AI-enabled extensions.

In \mync{coding with autocompletion}, the AI predicts the developer's intention by looking at existing code and comments, and automatically fills in the next few lines of code. The developer can modify the suggested content when necessary. Autocompletion is effective when the content to be filled is simple, self-contained, and pattern-wise consistent with the existing code. However, it may struggle to automatically generate long sections of code for complex functions. Examples include VS Code with GitHub Copilot extension.

In \mync{agentic coding}, the IDE is integrated with a chatbox. The developer can put comprehensive requests into the chatbox, and the AI can review, modify, or generate files in the project directory to achieve the goals. When AI agents modify the code, the developer can review the modifications in real time. The reviewer can accept or reject each change. The developer can raise new requests during development by interacting with the AI through the chatbox. If there is an error message, the AI can view the message and revise the code accordingly. Examples include VS Code with the GitHub Copilot extension in ``Agent'' mode. Different from coding with autocompletion, where the AI can access only (a portion of) the active file, in agentic coding AI agents are allowed to access almost all files in the project folder, and iteratively and recursively write and test code. This elevates the level of automation and requires much less human intervention. While AI agents can fully utilize everything in the project folder, they cannot reach out to the outside world, for example, to query the Internet for the latest libraries and learn something new on the fly.

In \mync{vibe coding}, there is not necessarily an \myabb{Integrated Development Environment}{IDE}. The developer puts requirements in markdown files before development, and starts the AI from the \myabb{command line interface}{CLI}. The AI reads the requirements, plans development procedures, and performs programming and testing iteratively. Different from agentic coding, the AI can equip MCP tools, skills, and plugins to better coordinate project development. For example, it can query the Internet for the latest user manuals for libraries, manage the project in Jira, update the project on GitHub, and so on. The developer can interact with the AI in the CLI using natural language. They can supervise the coding process if they wish. They can also leave everything to the AI, including programming, testing, debugging, and documentation. Examples include Anthropic Claude Code, OpenAI Codex, AMP, and VS Code with the GitHub Copilot extension in ``Plan'' mode.

Figure \ref{fig:vibe_coding_smartness} demonstrates the automation level of the different programming methods. For vibe coding, while being extremely automated, human would have less control and supervision over the product.
\begin{figure}[!htb]
	\centering
	\includegraphics[width=0.8\textwidth]{./chapters/part-4/figures/vibe_coding_smartness.png}
	\caption{Level of automation versus the level of control of the user over the code.}
	\label{fig:vibe_coding_smartness}
\end{figure}

In both agentic and vibe coding, programming can be done by multiple AI agents. In vibe coding, more complicated frameworks are supported, and the AI chooses the framework. Hence, vibe coding is often considered ``smarter'' and ``more automated'' than agentic coding. With vibe coding, it is possible to let the machine run by itself for a few days with no human intervention and the coding agent can iteratively design, implement, test and deliver the project. With the correct configuration, the vibe coding agent can even automatically check online information, communicate bidirectionally with the project online repository and the community, and even create developer tools to help it with the programming. However, as a trade-off, token consumption of vibe coding is often considerably larger than that of the agentic coding. The quality of the output largely depends on the precision of the instruction files and tools. It can be challenging for developers to work collaboratively with the AI to code or debug, due to the massive amount of code automatically generated by the AI.

In the context of vibe coding, the developer does not need to program a single line of code. Instead, they need to construct requirement documents and equip the AI with necessary tools. This role is known as the \mync{context engineer}, an expansion of the prompt engineer role.

\subsection{Pros and Cons}

While vibe coding is very powerful, as will be illustrated by the examples in the following sections, it has restrictions. Vibe coding is useful and effective when a project has the following features.
\begin{itemize}
  \item The project is at prototyping phase and the user needs a quick and smooth start, focusing on realizing functions rather than implementing precise details.
  \item The programming languages, libraries, and functions are well established.
\end{itemize}
For the above use cases, vibe coding can often save time and speed up the development.

On the other hand, vibe coding can struggle in the following scenarios.
\begin{itemize}
	\item The project is at the delivering phase and requires extremely precise coding for the optimal efficiency or consistency.
	\item The programming languages, libraries and functions are propriety or require a lot of precise configurations that only the user knows how they can be done.
\end{itemize}
The root cause of the above shortages is essentially the lack of human-in-the-loop supervision. As introduced earlier, vibe coding is so automated and so fast, that it is hardly possible for a human to intervene and supervise the details. When such effort is required, consider using agentic coding instead.

Recently, features such as skills and plugins, to be introduced in \ref{sec:advanced_coding}, have been proposed and they might be useful in tackling these issues. For instance, some skills or plugins may emphasize efficiency and consistency during the programming.

\section{Basic Vibe Coding}

This section introduces basic vibe coding with Claude Code. The details are given in \cite{claudeCode2026overview}. Many concepts and techniques introduced in this section can be transferred to other vibe coding tools such as OpenAI Codex.

\subsection{Installation and Initialization}

Claude Code can be installed on Windows, Linux, and macOS systems. For example, to install Claude Code on a Linux machine, use
\begin{lstlisting}
curl -fsSL https://claude.ai/install.sh | bash
\end{lstlisting}
in the terminal.

After installation, use the command \verb|claude| in the shell to start Claude. On the first start of Claude Code, the user needs to log in with either Claude account (with a Claude chatbot subscription) or a Claude API key.

Assume that the user is in an empty project root folder and from there Claude Code is started. The user can use the following command
\begin{lstlisting}
/init
\end{lstlisting}
to initialize the folder. Claude Code will create a \verb|CLAUDE.md| file in the project folder. The user can describe the project in the \verb|CLAUDE.md| file, and Claude Code will start coding accordingly.

With \verb|CLAUDE.md| and relevant explanatory documents ready, the user can ask Claude Code to start programming accordingly. The user can interact with the Claude Code agent using natural language from the \myabb{command line interface}{CLI}, giving it permissions, checking its progress, or asking it explain the design and implementation of the project. When Claude Code starts coding, it will create a \verb|.claude| folder to save files used by Claude Code. Unless the user wants to add skills, plugins, and sub-agents for Claude Code, the user does not need to review or modify anything inside the \verb|.claude| folder. More details about \verb|.claude| will be introduced in Section \ref{sec:advanced_coding}.

The \verb|CLAUDE.md| file, together with the \verb|.claude| folder, can be considered the minimum setup for a Claude Code-incorporated project.

The user can name a Claude Code session and later they can refer to the session or resume the session. In a Claude Code session, each round of a conversation and action is considered a checkpoint, and later a user can rewind a conversation.

\begin{lstlisting}
/rename <session-name>
\end{lstlisting}
to name or rename the current session. Use 
\begin{lstlisting}
$ claude --resume
\end{lstlisting}
and then follow the prompt to resume a session named in the past. 

Use
\begin{lstlisting}
/reward
\end{lstlisting}
and then follow the prompt to rewind to a historical checkpoint in the session. The user can restore the code or the conversation, or both.

Resuming a session does not change the content of the project folder. Rewinding may or may not restore the code, but it is not recommended to use rewinding to trace the progression of code. Use Git to trace the project progression and versions.

\subsection{Tool}

The concept of tools was first introduced in Section \ref{sec:introduction_to_agentic_ai} as an important feature of agentic AI frameworks. A similar idea applies in the context of vibe coding, where a \mync{vibe coding tool} helps a vibe coding engine such as Claude Code gain additional abilities relevant to programming and project management.

In this section, tools with \myabb{Model Context Protocol}{MCP} interface are introduced, as they have become increasingly popular and powerful, and are easy to install with Claude Code. \myabb{Model Context Protocol}{MCP} has been introduced in Section \ref{sec:mcp} and more details can be found there. In summary, MCP provides a scheme to share tools and other resources that can be consumed by AI agents and it allows an AI agent to use tools and other resources developed by the community. MCP has been widely adopted since its debut.

MCP-incorporated tools can be found on MCP marketplaces such as Official MCP Registry \cite{mcp2025registry}, MCP.So \cite{mcpso2026}, Glama \cite{glama2026mcpRegistry}, and many more. To install a specific MCP-incorporated tool with Claude Code, follow the instructions in the corresponding official repository. Very often,
\begin{lstlisting}
% claude mcp add <server name> [options]
\end{lstlisting}
is used in the shell to install a new MCP server with \verb|[options]| often containing the registry information, and
\begin{lstlisting}
$ claude mcp remove <server name>
\end{lstlisting}
to remove an MCP server.

Once an MCP-incorporated tool is installed, start Claude Code and use \verb|/mcp| command to check its status and options. An active MCP tool also consumes some context window, and hence \verb|/context| can also be used to check active MCP tools.

During vibe coding, the coding agent shall be able to use an MCP tool automatically when it thinks beneficial. The user can also explicitly ask Claude Code to perform certain tasks using an MCP tool.

\subsection{Skill} \label{sec:claudeskill}

While tools are packed functions in black boxes, a \mync{vibe coding skill} is verbally written instructions in markdown that teach the coding agent about a task. Sometimes skills can be interpreted as ``pre-written prompts''. Compared with tools, the use of skills has at least the following advantages and may become useful in many occasions.

\begin{itemize}
  \item Skills are more transparent and human-readable than tools.
  
  While tools are packed black boxes, skills are instruction documents in natural languages. The user can audit or customize skills more easily.
  
  \item Skills are cheaper and easier to develop and deploy than tools.
  
  Tools are essentially wrapped applications. To develop a tool from scratch, the user needs to program and pack functions, and develop associated APIs. To develop a skill, the user only needs to collect instructive documents. 
  
  The agent will read the instructions. When necessary, the agent may code a tool by itself following the instructions from the skills. In this sense, ``everyone can define skills'' even if they do not know anything about coding.
  
  \item Certain tasks are difficult to pack into functions, hence only doable with skills. 
  
  In some use cases, the additional information is hidden only in verbal descriptions and no tools can access them. For example, imagine that user wants the agent to program following their implicit ``habit'' consistently. The user can do so by collecting their own codes and use them as part of the skills. The agent can then learn the habit from the sample codes and behave accordingly.
\end{itemize}

Though easier to implement, skills are often less precise and sometimes not as powerful as a tool for complicated tasks. This is not surprising as tools are deterministic programs dedicated to a task, while skills are unstructured descriptive instructions. Nowadays, it is possible to include scripts that an AI agent can run locally, which mitigated the problem to some extent. However, it is still less systematic and powerful than a conventional tool such as an MCP based tool.

With Claude Code, the user can add a skill to the coding agent by creating a folder with the skill name under \verb|.claude| folder, and create \verb|SKILL.md| to describe the skill, as given in Fig.~\ref{fig:claude_vibe_tree}. More details about the skill directory is given below \cite{claudeCode2026skills}. Subfolders and supporting documents, if any, can be placed into the same skill folder. If the agent is expected to learn from sample codes, the codes can be put into the same folder as well.
\begin{lstlisting}
<skill name>/
|-- SKILL.md           # Main instructions (required)
|-- template.md        # Template for Claude to fill in
|-- examples/
|   \-- sample.md      # Example output showing expected format
\-- scripts/
    \-- validate.sh    # Script Claude can execute
\end{lstlisting}

In \verb|SKILL.md|, the name and a one-line description of the skill should be given, followed by detailed instructions. The instructions can spread into multiple subfolders and files. A simple example from \cite{claudeCode2026skills} is given below. In
\begin{lstlisting}
.claude/skills/explain-code/SKILL.md
\end{lstlisting}
add the following
\begin{lstlisting}
---
name: explain-code
description: Explains code with visual diagrams and analogies. Use when explaining how code works, teaching about a codebase, or when the user asks "how does this work?"
---

When explaining code, always include:

1. **Start with an analogy**: Compare the code to something from everyday life
2. **Draw a diagram**: Use ASCII art to show the flow, structure, or relationships
3. **Walk through the code**: Explain step-by-step what happens
4. **Highlight a gotcha**: What's a common mistake or misconception?

Keep explanations conversational. For complex concepts, use multiple analogies.
\end{lstlisting}
This skill teaches Claude Code how to explain a piece of code, should the user needs it to do so.

Skills are portable and can be easily shared across machines on different platforms. This is not surprising as they are documents in natural languages. There are market places for skills. For example, Anthropics defines skills in their GitHub repository \cite{anthropic2026skills} which can be accessed and downloaded freely. Other examples include Vercel's agent skills directory \cite{vercel2026skills}, and many more.

Skills are essentially documents and scripts that can be copy-and-paste to the repository. Nowadays, many skills registries allow the user to ``install'' skills, which is essentially a single line of command and the system will copy-and-paste relevant documents and perform the configurations.

\subsection{Plugin}

A \mync{vibe coding plugin} is essentially a pre-defined collection of tools, skills, configurations, etc., all packed together. Claude Code provides variety of official plugins and they can be easily installed and executed.

To manage plugins and plugins marketplaces, use
\begin{lstlisting}
/plugin
\end{lstlisting}
in Claude Code and follow the prompt. The \texttt{claude-plugins-official}, the official Claude plugin registry, should exist as the default marketplace. To install Claude Code official plugins, either follow the wizard, or use
\begin{lstlisting}
/plugin install <plugin name>@claude-plugins-official
\end{lstlisting}
To browse for the plugins, either follow the wizard or use
\begin{lstlisting}
/plugin > Discover
\end{lstlisting}

Once installed, the user can either ask the code agent to use a plugin using natural language, or call a plugin using
\begin{lstlisting}
/<plugin name> <options>
\end{lstlisting}
where \verb|<plugin name>| is either the name of the plugin, or the function name the plugin specifies. The options and goals of different plugins differ, and the user shall check the official website for the use of each plugin. 

Take \verb|ralph-loop| as an example. It is a plugin that allows the coding agent to iteratively program, test and improve the quality of the code. The instruction is given in \cite{claudeCode2026ralphWiggum}. To start \verb|ralph-loop|, use the following command in Claude Code
\begin{lstlisting}
/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"
\end{lstlisting}
With the above command, Claude Code will
\begin{enumerate}
	\item Work on the task.
	\item Try to exit upon completion of the task.
	\item A stop hook automatically triggers and stop Claude Code from exiting.
	\item The stop hook feeds the same prompt back to Claude Code.
	\item Claude Code re-do the task on top of its previous work, hopefully improving the quality.
\end{enumerate}
The above procedures are repeated for multiple times until either the agent thinks the goal of the task is fully achieved and there is no further room for improvement, or when the maximum iteration number is reached.

\subsection{Hook}

A \mync{vibe coding hook} refers to the mechanism that allows user-defined shell commands, HTTP endpoints, MCP tool calls, LLM prompts, or subagents to be executed automatically at specific points in Claude Code lifecycle \cite{claudeCode2026hooks}.

An example of hook from \cite{claudeCode2026hooks} is shown below. In \verb|.claude/settings.json| or \verb|.claude/settings.local.json| (the former can be committed to the repository hence sharable, while the latter is included in \verb|.gitignore| and hence not sharable), add the following hook.
\begin{lstlisting}
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "if": "Bash(rm *)",
            "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/block-rm.sh",
            "args": []
          }
        ]
      }
    ]
  }
}
\end{lstlisting}
Meantime, in \verb|.claude/hooks/block-rm.sh|, add the following shell script.
\begin{lstlisting}
#!/bin/bash
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0  # no decision; normal permission flow applies
fi
\end{lstlisting}

The purpose of this hook is to block destructive command \verb|rm -rf| that the vibe coding agent may accidentally trigger. It is triggered by event \verb|PreToolUse|. A full list of events at different Claude Code lifecycle that can trigger a hook is given in \cite{claudeCode2026hooks}.

\subsection{Self-Defined Command and Plugin}

With Claude Code, the user can introduce a self-defined command by creating a markdown file under \verb|.claude/commands|, with the command used as the file name. This is illustrated by Fig.~\ref{fig:claude_vibe_tree}.
 
The contents and the actions of the command should be illustrated in detail in the markdown file. Use \verb|$ARGUMENTS| in the markdown file to represent all arguments of the command, or use \verb|$1|, \verb|$2|, etc., to capture the positional arguments.

Skills, introduced in Section \ref{sec:claudeskill}, are also recognized as self-defined commands once they are installed.

The user can also add self-defined plugins to the project. A plugin structure looks like the following \cite{anthropic2026claudeCodePlugins}.
\begin{lstlisting}
plugin-name/
|-- .claude-plugin/
|   \-- plugin.json          # Plugin metadata
|-- commands/                # Slash commands (optional)
|-- agents/                  # Specialized agents (optional)
|-- skills/                  # Agent Skills (optional)
|-- hooks/                   # Event handlers (optional)
|-- .mcp.json                # External tool configuration (optional)
\-- README.md                # Plugin documentation
\end{lstlisting}
where \verb|plugin-name| should be a directory in \verb|.claude|, as shown in Fig.~\ref{fig:claude_vibe_tree}.

Self-defined plugins can be collected and registered as a self-defined marketplace. The entry to the configuration of plugins and marketplace is \verb|/plugin|. The user can follow the wizard to manage the plugins and wrap them into a new marketplace.

\section{Sub-Agent and Agent Team}

It is generally not recommended to open multiple windows and let multiple coding agents work simultaneously on the same project without knowing each other.

In agentic AI frameworks, an agent can call another agent as a tool for a specific task. Similar ideas apply to coding agents. In vibe coding, a coding agent can call sub-agents for specific tasks. Each agent has its own context window and they do not pollute the context of one another. Coding agents can form teams where one of the agents plays the manager and the rest playing different roles in the team, similar with CrewAI introduced in Section \ref{sec:crewai}. 

It is worth mentioning that some plugins may come with multi-agent coding framework and the user may have been using sub-agents and agent team without knowing them.

More details are introduced in the rest of this section.

\subsection{Sub-Agent}

Sub-agent allows the vibe coding main agent to delegate specific tasks to a sub-agents. It has at least the following benefits.
\begin{itemize}
  \item The main coding agent the sub-agents work in parallel, speeding up the project development, assuming that their work does not overlap.
  \item Each sub-agent has its own context window dedicated for the task assigned to it, and hence it is more focused on the task and would not pollute the context window of the main coding agent.
\end{itemize}
Notice that the user should mind the overlaps of tasks among the agents as well as any additional token cost.

In Claude Code \myabb{command line interface}{CLI}, use \verb|/agents| to view existing agents or follow the wizard to create a new agent. The user can also create an agent by adding documents in \verb|.claude/agents|, as shown in Fig. \ref{fig:claude_vibe_tree}. The name of the document should be consistent with the agent name. An example of a self-defined agent corresponding document is given below \cite{claudeCode2026subAgents},
\begin{lstlisting}
---
name: code-improver
description: Scans files and suggests improvements for readability, performance, and best practices. Use after writing or modifying code.
tools: Read, Grep, Glob
model: sonnet
---

You are a code improvement specialist. For each issue you find, explain
the problem, show the current code, and provide an improved version.
\end{lstlisting}
where notice that the name and the description of the sub-agent is given. The tools allowed for the agent and the model are optional.

To use a self-defined agent as a sub-agent, the user may specifically ask the coding agent to do so in the CLI, for example, by giving the following instruction.
\begin{lstlisting}
Use the code-improver agent to suggest improvements in this project.
\end{lstlisting}
It is essentially the main agent that decides to use a sub-agent.

\subsection{Agent Team}

\mync{Agent orchestration} refers to the technology used to manage the multiple agents working on the same project. Anthropic introduces \mync{Claude agent Teams} for agent orchestration that runs multiple vibe coding sessions. 

In this architecture, one session acts as the team lead that coordinates work, assigns tasks and synthesizes results whereas other sessions act as teammates that work independently and can directly communicate with each other. The user can interact with the team lead or directly with the teammates directly \cite{claudeCode2026agentTeams}.

Agent teams are most effective for tasks where parallel exploration adds real value. However, they add coordination overhead and use significantly more tokens than a single session \cite{claudeCode2026agentTeams}.

Figure \ref{fig:claude_vibe_agentteam} demonstrates the differences between sub-agent and agent team architectures. From the figure, it can be seen that sub-agent architecture has a clearer and explicit pipeline and tree structure when invoking sub-agents. Agent teams architecture, on the other hand, mimic a teamwork environment and hence does not have the same explicit pipeline and tree structure, but enables more flexible communications directly among the teammates, as indicated by the blue arrows.

\begin{figure}[!htb]
	\centering
	\includegraphics[width=0.8\textwidth]{./chapters/part-4/figures/vibe_coding_agentteam.png}
	\caption{Sub-agent architecture versus agent team architecture.}
	\label{fig:claude_vibe_agentteam}
\end{figure}

As of this writing, Claude agent teams are still an underdevelopment feature and it is by default disabled \cite{claudeCode2026agentTeams}. To use Claude agent teams, the user needs to enable it in \verb|settings.json| as follows.
\begin{lstlisting}
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
\end{lstlisting}

Once agent teams feature is enabled, instruct Claude to spawn teammates for a task. The user can specify the number and the tasks for the teammates, or they can leave it to the team lead. During the development of the project, the user can list down all the engaged agents including the team lead and the teammates, and interact with each of them directly.

\section{Sandbox}

Sandbox, both local and remote (for example, on Anthropic servers), provides a way to develop and test a project in harness and in a more parallel and automatic manner. 

The user can always use a \myabb{virtual machine}{VM} or a docker container as a sandbox to run vibe coding agent. However, this section focuses on naive sandbox features that come with Claude Code. Use \verb|/sandbox| to start of configure a local sandbox. The wizard is intuitive and the configuration simple, and hence they are not introduced in detail here.

To create a background session while using Claude Code, simply add \verb|&| in the beginning of the instruction. This will create a background task. To check all running background tasks, use \verb|/tasks|.

\section{Good Vibe Coding Practice}

The \verb|CLAUDE.md| serves as the instruction to the vibe coding agent, and it is worth the user spending time on crafting it carefully. Project summary, goals, successful criteria and code standards shall be included in \verb|CLAUDE.md|, and not the implementation or design details, which can come with \verb|README.md| or other designing documents. When the instructions spread in multiple files, use \verb|@<path/file>| to include the content of a file into a parent file.

The following rules are commonly used in \verb|CLAUDE.md| as the fundamental requirements to vibe coding agents.
\begin{itemize}
  \item Avoid overcomplicated development and testing procedures.
  \item Comments only when necessary.
  \item Be concise with README and do not use emojis.
  \item Avoid overly defensive programming and instance checks, and use exceptions only when necessary.
  \item Use \verb|uv| to manage libraries and use \verb|uv run xxx| but not \verb|python xxx| to execute a script.
\end{itemize}

Other than investing time in \verb|CLAUDE.md|, good practices with vibe coding includes the following.
\begin{itemize}
  \item Start from a simple prototype, and work incrementally, and validate success criteria in each iteration.
  \item Use intelligent models over fast models, especially in \myabb{You Only Look Once}{YOLO} mode.
  \item Challenge the design and choices instead of simply agree with all the decision the vibe coding agent makes.
\end{itemize}

The user is encouraged to ask Claude Code to plan before coding. For example, the user may ask Claude Code to split the project into multiple phases or stages, plan the tasks and tests for each phase, and save the plan in a file such as \verb|PLAN.md|. The user should check the plan and let Claude Code implement it phase by phase. After completion of development and testing for each phase, it is recommended that the user ask Claude Code to document the phase and commit the intermediate achievement.

The user is encouraged to check context window consumption after each step, especially when there are many steps in a complex project. Use \verb|/context| to check context window consumption. When the context window is about to be used up, the user is encouraged to do one of the following.
\begin{itemize}
  \item Use \verb|/compact| manually after reaching a milestone to compact the context window in between implementation phases.
  \item Ask Claude Code to summarize the progress and save it in a file such as \verb|README.md|. Clear the context window using \verb|/clear|, and let the new agent read the saved documentations and resume the development.
\end{itemize}
If possible, do not let Claude Code decide when to compact the context, as it may happen in the middle of developing an important and complicated feature.

In collaborative projects, it is important that the coding agent performs consistently among the collaborates. It is suggested to use consistent skills and plugins across different machines when they are working on the same project. Always involve human reviewer.

Troubleshooting and debugging code with vibe coding agents can sometimes be irritating. For simple bugs, it is possible that the vibe coding agent can fix the bug on the fly. If the user notices a bug, it is possible that the user simply needs to copy-and-paste the error message to the chat and the vibe coding agent would fix it in a few iterations. The user needs to check the implementation of the fix to make sure that there is no over-engineering.

For more complicated bugs, sometimes the vibe coding agent would try looking for solutions online, find something irrelevant, and jump to the conclusion that the fix had been found. To prevent that from happening, it is recommended that the user should challenge the fix, and let the agent document the process of the following.
\begin{itemize}
  \item Methods to reproduce the error or the bug consistently.
  \item Root cause of the problem.
  \item Fix of the problem.
  \item Lessons learned, to be documented in \verb|CLAUDE.md|.
\end{itemize}

Last but not least, the user owns the code. If the user cannot explain the code generated by the vibe coding agent, they the code is likely to be useless in the production environment.
